# Rudis — 시스템 설계 (v1: 핵심 KV 서버)

**목표:** Tokio 기반으로 만든, `redis-cli`와 호환되는 Rust 키-값 서버.
**핵심 방향:** Rust를 깊이 배우는 것 — 의존성이 학습 기회를 가려버리는 부분은 직접 구현한다.

---

## 1. 요구사항

### 기능 요구사항
- TCP 위에서 RESP2 프로토콜 지원 (`redis-cli`가 바로 붙는다)
- 명령어 (v1): `PING`, `ECHO`, `GET`, `SET` (`EX`/`PX`/`NX`/`XX` 옵션 포함), `DEL`, `EXISTS`, `EXPIRE`, `TTL`, `INCR`/`DECR`, `KEYS` (glob, 디버그용)
- 지연(lazy) + 능동(active) 키 만료

### 비기능 요구사항
- 수백 개의 동시 연결을 성능 저하 없이 처리
- p99 지연시간은 서버가 아니라 네트워크가 지배 (메모리 연산은 µs 단위)
- 우아한 종료(graceful shutdown): 신규 연결 중단 후 처리 중인 명령은 완료
- 단일 노드, 인메모리 전용 — 영속화·복제 없음 (v1)

### 제약사항
- 개발자 1인, 학습 중심 → 영리함보다 명료함 우선
- 의존성 최소화: `tokio`, `bytes` 정도만.
  **의도적으로 직접 구현:** RESP 파서 (`redis-protocol` 크레이트 미사용), 샤딩 저장소 (`dashmap` 미사용), glob 매처.

## 2. 상위 아키텍처

```
                    ┌──────────────────────────────────────────┐
                    │               Rudis 서버                  │
                    │                                          │
  redis-cli ──TCP──▶│  리스너 ──spawn──▶ 연결(Connection) 태스크 │
  클라이언트A ─TCP──▶│  (accept 루프)      ┌────────────────┐   │
  클라이언트B ─TCP──▶│                     │ 프레임 디코더    │   │
                    │                     │ (RESP 파서)     │   │
                    │                     └───────┬────────┘   │
                    │                             ▼            │
                    │                     ┌────────────────┐   │
                    │                     │ 명령 파싱 +      │   │
                    │                     │ 디스패치         │   │
                    │                     └───────┬────────┘   │
                    │                             ▼            │
                    │        ┌─────────────────────────────┐   │
                    │        │  Db (Arc로 공유)             │   │
                    │        │  ┌───────┐ ┌───────┐        │   │
                    │        │  │샤드 0 │ │샤드 1 │ …       │   │
                    │        │  │ Mutex │ │ Mutex │        │   │
                    │        │  └───────┘ └───────┘        │   │
                    │        └─────────────▲───────────────┘   │
                    │                      │                   │
                    │        만료 스위퍼(sweeper) 태스크 (능동)   │
                    └──────────────────────────────────────────┘
```

**데이터 흐름:** accept → 연결마다 태스크 spawn → 버퍼로 바이트 읽기 → RESP 프레임 디코드 → `Command` enum으로 파싱 → `Db`에 대해 실행 → RESP 응답 인코드 → 쓰기.

## 3. 모듈 구성

```
src/
  main.rs          // CLI 인자(포트), tracing 설정, 서버 실행
  server.rs        // accept 루프, 연결별 태스크, 종료 브로드캐스트
  connection.rs    // 버퍼링된 읽기/쓰기, 프레임 경계 처리
  resp/
    mod.rs         // Frame enum: Simple, Error, Integer, Bulk, Array, Null
    parse.rs       // bytes -> Frame (증분 파싱, 부분 입력 처리)
    encode.rs      // Frame -> bytes
  cmd/
    mod.rs         // Command enum + 디스패치; Frame -> Command 파싱
    get.rs, set.rs, del.rs, expire.rs, incr.rs, ...  // 명령어당 파일 하나
  db.rs            // 샤딩 저장소, Entry {value, expires_at}, 스위퍼
  shutdown.rs      // 우아한 종료 신호 배선
```

모듈별로 강제로 익히게 되는 Rust 개념: `resp/` — 바이트 버퍼의 소유권, `Bytes` vs `Vec<u8>`, 복사 없는 증분 파싱; `db.rs` — `Arc`, `Mutex`, `Send + Sync` 바운드, 내부 가변성; `server.rs` — 태스크, `select!`, 취소(cancellation); `cmd/` — enum, 패턴 매칭, 트레이트 설계.

## 4. 핵심 결정과 트레이드오프

### D1. 동시성: Tokio 태스크 + 공유 상태 (액터/채널 모델 아님)
연결마다 태스크가 `Arc<Db>`를 들고, 명령 처리 시 짧게 락을 잡는다.
- (+) 단순하고 직접적; `Arc`/`Mutex`를 제대로 배운다; mini-redis 선례와 일치
- (−) async 코드에서 락은 주의 필요: **`std::sync::Mutex` 가드를 `.await` 너머로 절대 들고 가지 않는다** — 태스크가 소켓 쓰기를 await하기 전에 응답을 전부 계산해 둔다
- 기각한 대안: mpsc 채널로 명령을 받는 단일 "db 액터" 태스크 — 격리는 깔끔하지만 공유 메모리 학습 포인트를 가리고 지연이 한 홉 늘어난다
- 재검토 시점: `BLPOP` 같은 블로킹 명령이나 pub/sub 추가 시 — 그때는 채널/액터 패턴이 값어치를 한다

### D2. 저장소: 직접 만든 샤딩, `Vec<Mutex<HashMap<String, Entry>>>` (N = 16)
키 → 해시로 샤드 결정; 샤드당 `std::sync::Mutex` 하나 (가드가 `.await`를 넘지 않으므로 문제 없음).
- (+) 전역 병목 없는 동시성; `dashmap`이 대신 해주는 일을 직접 구현해 본다
- (−) 여러 샤드를 건드리는 멀티 키 명령은 락 순서 규율 필요 (v1은 회피: `DEL k1 k2`는 샤드를 하나씩 잠근다)
- 재검토 시점: `MULTI`/트랜잭션이나 원자적 멀티 키 연산이 필요할 때

### D3. 만료: 읽기 시 지연 확인 + 능동 스위퍼 태스크
읽기는 만료된 엔트리를 없는 것으로 취급하고 삭제한다. 백그라운드 태스크가 100ms마다 깨어나 샤드별로 무작위 키를 샘플링해 만료분을 제거한다 (Redis 자체 전략).
- (+) 스윕 비용이 유계; 키별 타이머 태스크 없음 (그건 태스크가 O(키 수)가 된다)
- (−) 만료됐지만 읽히지 않은 키의 메모리 회수가 지연됨
- 기각한 대안: (만료시각, 키)의 `BinaryHeap` — 정밀하지만 무효화된 엔트리 처리가 까다로움; v2 연습 문제로 적합

### D4. 프로토콜: RESP2, 직접 작성한 증분 파서
파서는 `BytesMut` 읽기 버퍼에서 소비하며 `Ok(Some(frame))`, `Ok(None)`(바이트 더 필요), `Err`(프로토콜 위반 → 연결 종료)를 반환.
- (+) 이 프로젝트에서 가장 배울 게 많은 부분: 프레이밍, 부분 읽기, 제로카피 슬라이싱
- (−) 버그 표면적이 넓다 → 퍼징 스타일 단위 테스트 (유효한 프레임을 모든 바이트 경계에서 잘라 검증)

### D5. 에러: 레이어별 `thiserror` enum, 라이브러리에서 `anyhow` 미사용
프로토콜 에러는 연결을 닫고, 명령 에러(타입 불일치, 숫자 아닌 값에 `INCR`)는 RESP `-ERR ...` 응답이 되며 연결은 유지된다. 학습 포인트: 전부 박싱하는 대신 에러 타입과 `From` 변환을 설계해 보기.

## 5. 신뢰성과 운영
- **우아한 종료:** `ctrl_c` → broadcast 채널 → 연결 태스크는 현재 명령을 끝내고 플러시 후 종료; 리스너는 accept 중단. `tokio::select!`와 취소 안전성(cancellation safety)을 배운다.
- **백프레셔:** 연결당 처리 중 명령 1개 (읽기 → 실행 → 쓰기 루프) — 무한 큐 없음.
- **한계값:** 최대 프레임 크기 (Redis처럼 512MB, 더 작게 설정 가능); 초과 프레임 → 에러 + 연결 종료.
- **관측성:** `tracing`으로 연결별 span (피어 주소, 연결 id); 스위퍼가 카운터 로깅 (키 수, 만료 제거 수).

## 6. 테스트 전략
- 단위: RESP 파서 라운드트립, 모든 분할 지점에서의 부분 입력, 잘못된 프레임
- 단위: `tokio::time::pause()`로 결정적 시계를 만들어 `Db` 만료 시맨틱 검증
- 통합: 임시 포트에 서버를 띄우고 RESP를 말하는 raw TCP 클라이언트로 구동
- 인수: `redis-cli` 수동 세션; 나중에 `redis-benchmark`로 재미 삼아 수치 측정

## 7. 마일스톤
1. **에코 서버:** accept 루프 + 연결 태스크 + 우아한 종료 (RESP 없이)
2. **RESP:** 파서 + 인코더, `PING`/`ECHO` — `redis-cli`와의 첫 대화
3. **저장소:** `GET`/`SET`/`DEL`/`EXISTS`, 먼저 단일 샤드로, 그다음 샤딩
4. **만료:** `SET EX`, `EXPIRE`, `TTL`, 지연 확인, 그다음 스위퍼
5. **마무리:** `INCR`/`DECR`, `KEYS`, 한계값, tracing, 통합 테스트

## 8. 성장하면서 재검토할 것
- 풍부한 자료형 (List/Hash/Set) → `Entry`에 `enum Value`, 타입 불일치 에러
- 블로킹 명령 / pub-sub → 키별 대기자(waiter) 등록 (채널 모델이 돌아올 자리)
- 영속화 (AOF) → 디스패치 레이어에 명령 로그 훅, 이미 자연스러운 이음새가 있음
- RESP3 → `HELLO`를 통한 프로토콜 협상

**가정:** 단일 노드; 신뢰된 네트워크 (v1에는 AUTH/TLS 없음); 키/값은 바이트일 뿐 인코딩 무관; TTL에는 단조 시계(`Instant`) 사용.
